## 关键设计

- **v1/v2 仅限 /ai/chat（2026-08-30 用户定）**：业务 endpoint 不属于 v1/v2 之争——
  文件永存、路径不变；@mcp_tool 直接写在业务 endpoint 的 @tool 旁边（同一函数
  双注册，装饰器均返回原函数，FastAPI 无感，HTTP 行为零变化）。
- **双注册语义**：@tool 与 @mcp_tool 签名一致（name + result_formatter），各自注册
  到自己的体系——短期共存（v1 agent 用 @tool、v2 agent 用 @mcp_tool）；后期删
  @tool 机制（装饰器行 + tool_registry）即完成切换，业务文件不动、@mcp_tool 保留。
- **MCP 模式执行链**（同 v1 ToolDef.execute）：解包 api_success → _to_dict
  （model→dict，跳过 created_at/updated_at 防 MissingGreenlet）→ result_formatter
  输出 JSON 字符串（LLM 读 formatter 投影，隐私由 formatter 删减）。
- **Pydantic model 展平**（同 v1 _flatten_model）：create_post 的 content/images、
  create_comment 的 parent_comment_id 等展平为独立 schema 字段，执行时按字段重建
  model 实例——写操作工具（4 个）可完整 v1-copy 语义。
- **注册触发**：MCP server（tools/mcp_server/main.py）不 import 业务模块——app.main
  import v1 业务文件（路由本来就需要）时装饰器执行即注册，先于 mcp_app 构建。

## M3 演进定案（2026-08-31 用户 review 提出）

用户不喜欢"通过 session_id 编码 user_id"的传递方式。调研全部替代通道（Python SDK 无
metadata 参数、DSH session/scope 无业务字段、MCP SDK requestInit 连接级会串号、
fastmcp 读 header 需侵入、cordis 无 middleware、sdk-jsonrpc-server 不透传自定义
字段）——**M2 约束下 session_id 编码是唯一零侵入通道**（SDK `harness.run` 只接受
session_id）。

**定案：身份查询插件（M3）**——session_id 恢复纯 uuid，FastAPI 维护
session→owner 映射（JWT 处权威，并入 M3 sessions 表 owner_user_id），桥插件
execute 时 HTTP 查询 FastAPI 内部身份端点拿 user_id → 注入 _meta。M2 保持现状
（session_id 编码），TECH_SPEC §6.3/§8.2/§14 已标注演进路径。
