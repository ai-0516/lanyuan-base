### 决策记录

1. **缓存命中方案**：relevant 拼 user 消息而非 system——因为 DeepSeek 前缀缓存对 system 变化敏感，user 消息序列末尾变化不影响前缀命中
2. **模块级函数签名**：`select_relevant(db, user_id, message)` 不再传 provider——provider 是内部细节，调用方无感知
3. **FK 与 index**：FK 自带索引（MySQL），显式 index 冗余删除；SQLite 下 FK 不自动建索引但表小（每用户 ≤30 条）无性能问题

### 三轮 review 补充（16:30 用户追加 9 条意见，commit `cbb5463`）

**缓存设计 bug（用户 #4 指出，属实）**：原实现把 relevant 拼进「最后一条 user 消息」，但历史消息从 DB 读出时不带 relevant → 同一 user 消息两轮请求字节不一致 → 前缀缓存从第一条历史就断，只剩 system 命中。按 **Hermes 硬不变量**（system prompt byte-stable + 新内容只追加末尾）修复：**索引 + 相关记忆都拼 SYSTEM**（记忆不变则字节不变），历史消息绝不改写。查证 Hermes 源码：`memory_manager.build_system_prompt()` 注入 SYSTEM；system_prompt.py 用 date-only 时间戳保证整天字节稳定（注释明言分钟级变化会 invalidate prefix-cache）。learn-claude-code s09 同思路（索引进 SYSTEM，相关记忆注入 user 消息副本不污染原始 messages）。
