## 今日成果

### 🎯 AI Tab 从零搭建（harness 模块化）

将 `ai_service.py` 的单体代码拆分为独立模块，实现对 learn-claude-code 架构模式的本地适配：

```
backend/app/harness/
├── __init__.py          包声明
├── agent.py             纯 LLM 循环（AIAgent）—— 只负责与 LLM 交互
├── context.py           上下文窗口 + System Prompt
├── session.py           会话创建/查找/校验（用户隔离）
├── memory.py            消息持久化（用户消息、AI 回复写入 DB）
├── streaming.py         DeepSeek API 流式传输 + 工具解析
└── tools.py             create_post 工具定义 + 执行
```

**架构设计：**  
- `AIAgent` = 纯 LLM 层（messages in, events out, 不碰数据库）  
- `ai_service.py` = 编排器（数据准备 + 持久化协调）  
- 瞬态实例：每次对话新建，用完即弃

## 关键决策

- **分四层实现：** Session → Context → Agent → Tool。不追求一口气完成，每一步独立可测  
- **AIAgent 纯 LLM 层 + ai_service 管理器的分层：** 参考 learn-claude-code 思路，但适配到项目已有代码结构  
- **瞬态 Agent 实例：** 不搞 Agent 复用池，简单可靠  
- **不抄事件名、不抄参考代码集成点：** 理解设计思路后重新设计适配本地架构

## 遇到的技术挑战

1. **LLM 幻觉（不调 create_post 工具）** — 用户要求发帖，AI 回复"已发布"但没调工具  
   - 尝试：强化 System Prompt ❌ 无效  
   - 尝试：修复 context window 取最近 20 条（原来是取最早 20 条） ❌ 无效  
   - 创建 `docs/llm-issues.md` 记录问题追踪，留待明天解决  

2. **DeepSeek System Prompt 权重偏低** — 模型对 system 角色的指令敏感度低于对话示例  

3. **前端组件 observer 时序** — 微信小程序 observer 触发时机不可靠，改为父页面预处理

## 经验教训

- **不要在修复 bug 的同时写新功能** — 上午修前端 bug，下午搭 AI 底层，注意力切换成本高  
- **LLM 幻觉根因怀疑方向正确** — 历史中存在 AI 自己编写的"已发布"假回复，模型倾向于模仿自己的历史行为  
- **文档先行** — 先写 `ai-implementation-note.md` 和 `ai-harness-notes.md` 讨论草稿再写代码，比直接写代码少走弯路
