### 背景

session 的长期目标（用户提出）：**用户完全对 session 无感，session 的创建和管理完全在后端实现**。现有实现唯一创建 session 的方式是前端 `/new`（临时方案）。围绕「压缩 = 建新 session 时机」的设想，全天调研 Hermes 的 session 管理并逐项定案。

### 调研：Hermes session 管理（参考 ~/.hermes/hermes-agent）

- **session-lifecycle 模型**（gateway/session.py）：session_key（会话车道）→ session_id（会话化身）两层；状态机 flags（suspended/resume_pending/is_fresh_reset/was_auto_reset）；重置策略 none/idle/daily 每平台可配
- **关键发现：Hermes 已有「压缩旋转 session」完整实现**（agent/conversation_compression.py + context_compressor.py）：
  - `compress_context` 会 split SQLite session + rotate session_id（两种模式：in_place 默认 / rotation legacy）
  - rotation = `publish_compression_child(parent, child, system_prompt=new, messages=compressed)` 原子事务
  - `protect_last_n=20` 按消息数保护尾部（UI 无感的关键机制）
  - 压缩前 `commit_memory_session` 抽取记忆；旋转后 memory `on_session_switch`；goal 迁移、标题编号延续
  - 失败处理：原子发布失败 → 保持 parent 存活、返回原消息、不旋转
- **session_search 工具**（tools/session_search_tool.py）：四形态单工具（DISCOVERY/SCROLL/BROWSE/READ），FTS5 + lineage 去重 + bookend；底层 SQLite FTS5（external-content + trigger + CJK 中文索引）
- **Hermes 是有感的**（压缩发 "Compacting context" 状态消息、重置注入通知）——我们的「完全无感」比 Hermes 更进一步

### 关键讨论/教训

- **我犯的错**：① 说「tail 复制不会重复渲染」——用户抓住矛盾（复制 + 时间混排必然重复），修正为**迁移（move）**；② 为「system_prompt 用最新记忆」绕开事件系统提出同步抽取——用户纠正：保持事件驱动异步（摘要兜底 + 跨轮次查询时已就绪），编排层不越俎代庖
- **LLM 感知压缩 tool 调用**：必须看到（role 交替合法性 + 摘要要进上下文）；无误解风险（LLM 无外部信息源判断真伪，且压缩确实发生）
- **缓存 vs LRU 分离**：缓存（session 冻结）是前缀缓存命中的支柱（核心）；LRU 是「不知道谁该死」的通用兜底，我们有明确的 session 结束点（rotation）→ 精确清理优于通用淘汰
- **技术选型**：SQLite FTS5 有先天搜索优势但微信云托管（容器易失 + 多实例）下不成立——MySQL FULLTEXT + ngram 是同等能力面（倒排索引 + 相关度 + 中文分词）
