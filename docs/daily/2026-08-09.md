## 1. max_tokens 调研（问题驱动）

用户问 pi 项目 commit `c185d4123`（"fix(ai): send max_tokens to DeepSeek APIs"）与我们项目的关系，查证结论：

- **语义**：max_tokens = 单次回复输出上限；DeepSeek 只认 max_tokens，发 max_completion_tokens 直接 400（pi 修的正是字段名错配）
- **我们的对应改动**：commit `5c64913`（#53 review 落实）把 anthropic adapter 的 `DEFAULT_MAX_TOKENS` 4096→8192（Anthropic 端点 max_tokens 必填，该值真实发到服务端）——与 pi 是同一硬币两面：pi 修字段名，我们改字段值
- **「默认 4096」已过时**：4096 是 V3 时代默认（V3：默认 4096、上限 8192）；V4 pricing 页只写 MAX OUTPUT 384K 未写默认值；实测超大 max_tokens（99999999）被静默 clamp 不报错——「靠 400 探测上限」方案证伪
- **dev-server 网络坑**：HTTP 代理（127.0.0.1:7890）会 reset DeepSeek TLS 连接（SSL error 35），直连测试必须 `--noproxy "*"`

## 2. evals 调研三轮（#54/#55）

用户对 eval 是新领域，要求广泛调研再落地。三轮调研：

| 轮次 | 结论 |
|---|---|
| ① 框架选型 | 平台型（langfuse 32k★/phoenix/AgentOps）排除；openai/evals 仅参考打分器；**hermes-agent `toolperf_ab_eval` 为方法论骨架**（数据驱动任务 + ATOF trace 评分，字段与我们 jsonl 同源） |
| ② 方法论 | hermes 四要点：数据驱动陷阱任务 / 100% 确定性成功判定 / trace 指标（not self-report）/ 弱模型出信号；LLM-as-judge 仅限主观质量 |
| ③ 热门项目深挖 | 吸收 8 个设计点：**配置三分离**（Margin）/ **bootstrap 置信度**（simple-evals）/ 样本与逻辑分离（openai）/ baseline 标配（msft+pi）/ trace 复用（raindrop+hermes）/ 可复现 bundle / CI 集成 / 确定性优先 |

**策略调整**（用户拍板）：dev-server 是测试环境、无生产数据 → 「从生产数据量错误类别」不成立 → **架子优先，数据后补**（报告器 → harness → 手工测试集，将来有真实 jsonl 再补数据驱动任务）。

**运行形态两档**（用户拍板）：无 LLM 类（报告器/确定性评测）→ pytest + CI 可跑；有 LLM 类（跑 agent，花钱）→ **仅独立命令 + `--llm` 门控**，CI 不挂。

**hermes eval 执行时机**（用户追问）：手动批量、专项触发（改工具层代码时），不进 CI 无定时——印证我们「按需手动 + 门控」的设计。

## 4. #57 评测 harness 框架（PR #61 review 中）
