# Dev — 实现总结

## 背景

Issue #15：harness 模型厂商/消息格式抽象（Adapter）——当前写死 DeepSeek（OpenAI 兼容格式），需支持 Anthropic 等非 OpenAI 兼容协议。触发条件（支持 2+ 协议格式）**已满足**：DeepSeek 官方提供 OpenAI + Anthropic 两个协议端点，同一个 key 可同时验证两条路径。

## 调研：pi-ai 多厂商抽象设计（学习目标）

`earendil-works/pi` monorepo 的 `packages/ai`（v0.84.0，40+ providers）三个可借鉴点：

1. **Canonical 消息格式**：content 是 block 数组（text / thinking / toolCall / toolResult 四种 block 类型），与 Anthropic content blocks 天然同构。AssistantMessage 带 provider/api/model 元数据（跨模型 handoff 判断用）
2. **两段式转换**：
   - 第一段 `transformMessages()`（canonical→canonical）：跨厂商兼容性修复——tool call ID 规范化（OpenAI 450+ 字符 vs Anthropic ^[a-zA-Z0-9_-]+$ max 64）、图片降级、thinking 跨模型处理、孤儿 toolCall 合成空 toolResult、跳过 error/aborted 消息
   - 第二段 `convertMessages()`（canonical→厂商协议）：各家各写，纯翻译
3. **对称响应解析**：各家 SSE 流解析后归一成 canonical AssistantMessage（content blocks + stopReason + usage）

## 关键发现（代码调研）

- **Message 表是列式存储**（role / content / tool_calls JSON / tool_call_id 分列），结构中立——**不需要数据库迁移**，canonical ↔ 列是简单映射
- 耦合点全景：streaming.py（请求 + SSE 解析）、agent.py L257-270（回填 OpenAI 形状）、context_compact.py（配对判断判 `role=="assistant"`+`tool_calls`）、context.py `build_deepseek_messages`（ORM→OpenAI）、ai_service.py（`_to_openai_messages` + rotation 硬编码 compress_context）、config.py（DEEPSEEK_ 前缀）
- 数据流定案：**canonical 贯穿 agent 层和压缩层，协议转换只发生在 streaming 边界**

## PR #53 review 意见（snxly，4 条）→ 已采纳

1. **tool_name / is_error 应该保留** → 采纳：`tool_name` NotRequired（agent 回填必带，DB 回读按 tool_call_id 匹配）；`is_error` 默认 False（映射 agent 已有但丢弃的 `tool_status`；Anthropic `tool_result` 原生支持，OpenAI 侧忽略）
2. **thinking 能否区分答复 vs 推理** → 能：`block.type` 就是区分（thinking=推理 / text=答复），to_openai 折叠回 `reasoning_content`、to_anthropic 直译 thinking block，双向保留语义
3. **抽象 LLMAdapter 类**（用户建议）→ 采纳：`LLMAdapter(ABC)` 含 `canonical2llm` / `llm2canonical` 两个抽象方法，OpenAIAdapter / AnthropicAdapter 子类；streaming 通过 provider 查表拿实例，不写 if/else——比我的函数式方案更干净
4. **SDK 问题** → 不引入 openai/anthropic 官方 python SDK：手写 httpx SSE 恰是需要精细控制（reasoning_content、tool_calls 增量合并、错误体分类、断流检测），SDK 传输层是负资产；pi-ai 同场景自研传输层印证
