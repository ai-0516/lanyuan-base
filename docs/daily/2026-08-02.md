# Dev — 实现总结

### 成果

1. **Issue #27 统一错误响应格式**（PR #31）：
   - 根因：Starlette 对 `HTTPException` 是**精确键查找**，只注册 `Exception` 处理器时 401/404/422 走默认格式（顶层无 `code`），前端统一错误处理失效
   - 修复：注册 `StarletteHTTPException` + `RequestValidationError` 处理器；`api_exception_handler` 对无 detail 的 404 补默认文案（原来 `str(None)` → "None"）
   - **实测发现 FastAPI 0.141.1 重构**：`RequestValidationError` 已不是 HTTPException 子类（MRO: `RequestValidationError → ValidationException → Exception`，无 `detail`/`status_code`），不能复用 `api_exception_handler`，新增专用 `validation_exception_handler`（取首条错误的 `msg` 作为 message）
   - 修复后 401（40100）/ 404（40400）/ 422（42200）/ 业务错误均为 `{code, message}` 统一格式
2. **Issue #28 Like 外键约束**：
   - 模型加 `ForeignKey`（`posts.id` / `users.id`，`ondelete="CASCADE"`）；SQLite 显式开 `PRAGMA foreign_keys=ON`（SQLite 默认不强制外键）
   - 服务层 `like_post` 先校验帖子存在，不存在返回 `(None, 0)` → API 层 `40401 "帖子不存在"`（业务失败≠系统异常，避免 FK 抛 IntegrityError → 500）
   - 迁移 `28d5e00fd033`：先清存量孤儿数据再按方言建 FK（SQLite `batch_alter_table` / MySQL `create_foreign_key`）
3. **测试**：新增 7 个（服务层：FK 拒绝孤儿行 / 级联删除 / 点赞不存在帖子；API 层：401/404/422 统一格式 + 点赞业务错误），更新 e2e 旧断言（原断言依赖无 FK 的 bug 行为）；`pytest` 170 passed，ruff 通过
4. **流程**：`dev-team` skill disable（kanban 流程废弃，统一走 GitHub Issue→Branch→PR 流程）；doc 规则更新（merge 前强制 → dev 自定时机但必须写）

### 决策记录

1. **40100 语义**：无 token 走 HTTPBearer 默认 401（detail 为字符串 "Not authenticated"），统一后 `code=40100`；带无效 token 的 40101/40102 保持原样（TECH_SPEC 错误码表补 40100 行）
2. **服务层校验优先于 DB 约束兜底**：`like_post` 先查帖子存在性返回业务错误，DB FK 是最后防线（防直接 SQL / 绕过服务层的调用）
3. **迁移双方言**：SQLite 不支持 `ALTER TABLE ADD CONSTRAINT` 需 batch 重建；MySQL 直接 `create_foreign_key`；孤儿数据先清否则 MySQL 建 FK 失败

### 教训

- **config.yaml symlink 坑（第二次发生）**：Hermes `save_config` 用原子写（临时文件 + rename）会把 symlink **替换成独立文件**。配置真身在 `workspace/my-hermes/`（git 仓库），profile 目录下是指针；改配置后必须 `ls -la` 检查并恢复
- **re-dump 污染**：`save_config` 重写会改键顺序、可能污染部分值（本次 `max_iterations`/`tool_preview_length` 曾与真源不一致），以 `workspace/my-hermes` 真源为准恢复
- **验证迁移不要在 SQLite 上跑全链**：旧迁移 `f468c671cbff`（avatar TEXT）是 MySQL 语法 `ALTER COLUMN`，SQLite 会挂；应单独 stamp + 手工建旧结构验证新迁移
