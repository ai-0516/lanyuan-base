## 关键决策 🔑

### 1. 三层错误恢复架构

```
L1 退避重试（streaming.py）   ← 429/529/timeout 指数退避
L2 降级模拟回复（agent.py）   ← 重试耗尽/不可重试
L3 绝对兜底（ai_service.py）  ← 未捕获异常
```

可重试的错误在 streaming 层透明处理，前端无感知。只有重试耗尽后才降级。

### 2. 错误码设计：Enum + 策略表

```python
class LLMStatus(str, Enum):
    RATE_LIMIT = "rate_limit"       # 429 → 退避 3 次
    OVERLOADED = "overloaded"       # 529 → 退避 3 次
    AUTH_FAILED = "auth_failed"     # 401 → 直接降级
    SSE_DISCONNECTED = ...          # 断流 → 重大日志
```

策略用 `RETRY_CONFIG` dict 驱动，新增错误码只需加一行配置。

### 3. 日志在源文件记，不走 hook

讨论后决定重大日志直接在各 .py 里通过 `logger.exception/error` 记录。原因：①异常位置一目了然（文件+行号）；②日志内容灵活，不受事件数据结构限制。

### 4. 跳过 s03 Permission 和 s05 Todo Write

- **Permission**：工具都是后端 API，不存在本地权限问题
- **Todo Write**：社区助手任务简单，不需要任务规划

## 技术挑战 🧩

### 流式重试的边界问题

**问题**：SSE 已经开始返回 token 了，中间断流怎么重试？

**方案**：断流不重试，记 `_critical_error` 日志。因为重试会导致前端看到重复 token，续流实现复杂且断流概率低。等后续流式恢复方案再补。

### 重试时缓存事件的取舍

**问题**：第一次调用返回了部分 token 然后报错，第二次调用成功返回了完整结果。第一次的 token 要不要 yield 给前端？

**答案**：不 yield。`retry_deepseek_chat()` 把 token 缓存在 `buffered_events`，只有最后一次成功的结果才 yield。避免前端看到 "hellogoodbye"（第一次 hello + 第二次 goodbye 拼接）。

### async generator 的 retry 实现

streaming.py 的 `deepseek_chat()` 是 async generator，不能用常规的 try/except + while 循环包裹。方案是用一个 wrapper generator 内部调用 deepseek_chat，捕获 error 事件后回退重试。
