# Dev — 实现总结

## 背景

用户从本地小程序连 dev-server 时帖子加载失败（`GET /api/v1/posts` 500），重新登录后恢复；查 `backend/logs/error.log` 无任何记录。两个问题：① 事故根因；② error.log 为什么没记录。排查定位两个根因，开 issue #64 修复（PR #65，dev-lead 已 Approve）。

## 1. 问题一：帖子接口 500（瞬态故障）

journald 定位事故现场（10:20:40）：

```
GET /api/v1/auth/check → 200（登录态正常）
GET /api/v1/posts?page=1&size=20 → 500
pymysql.err.OperationalError (2013, 'Lost connection to MySQL server during query')
出错 SQL: SELECT count(posts.id) FROM posts
```

**根因**：SQLAlchemy 连接池（`pool_size=10/max_overflow=10`，未配 `pool_recycle`/`pool_pre_ping`）复用了被 MySQL 端关闭的僵尸连接。MySQL `wait_timeout=28800`（8h）会回收空闲连接，池内连接失效后 TCP 层不感知，查询中途断开报 2013。失败后该连接被池剔除，后续请求全部正常——**与用户重新登录无因果关系，重试即恢复**，一次性瞬态故障。

## 2. 问题二：error.log 未记录（真正的 bug）

`logs/error.log` mtime 停在 8/9 15:46（当天零写入），而 8/9 那 4 行 LLM 错误是业务代码主动打的（`ai_service` 等），非异常处理器打的。

**根因**：`api_exception_handler` 用 `hasattr(exc, "detail")` 判断 HTTPException，但 **SQLAlchemy 数据库异常（OperationalError/ProgrammingError）恰好自带 `.detail` 属性（值为 `[]`）** → SQL 异常被误判进 detail 分支：
- 返回误导性文案 `{"code":50000,"message":"Not Found"}`（本应"服务器内部错误"）
- **该分支无任何日志** → error.log/app.log 永无记录

**后果**：所有 SQL/DB 异常不进日志，500 只能翻 journald。

### 排查中的关键认知

1. **starlette 1.3.1 的 `ServerErrorMiddleware` 无论 handler 是否成功处理都会 `raise exc`**（"We always continue to raise"）→ journald 出现 "Exception in ASGI application" + 完整 traceback **不代表 handler 没执行**。判断 handler 是否执行的依据是**应用日志**（`logger.exception` 的 "未捕获的异常" 是否出现），不是 uvicorn 的兜底日志。这个误判让排查绕了弯路。
2. **`fastapi.HTTPException` ≠ starlette 的 `HTTPException`**（0.141.1 实测）：`fastapi.exceptions.HTTPException` 是独立类，只是 starlette 的子类，不是 re-export。handler 内 `isinstance` 判断必须用基类 `StarletteHTTPException`（业务 `api_error` 抛 fastapi 子类、路由 404/401 抛 starlette 本体，基类判断两者都覆盖）。若用 `fastapi.HTTPException`，路由 404 会被漏判成非 HTTPException → 500 回归（全量测试抓到的坑）。
3. 实证链：dev-server TestClient 加载真实 app 复现（500 + `Not Found` + error.log 零写入）→ `hasattr(OperationalError, "detail")` == True 石锤。

### 4.1 CI eval job 静默失败（用户反馈「报告只有单元测试段」）

用户发现 PR 评论里 ATOF 报告器和测试集加载段空白，但 CI 全绿。查日志定位两个问题叠加：

1. **解释器与依赖不一致**：setup-uv 设 `UV_PYTHON=3.11`，但 `pip install` 实际把依赖装进 python3.12 user site（cp312 wheel）→ `pytest` 命令（3.12）能跑 56 passed，`python` 命令（3.11）无 pydantic_settings → ATOF/tasks step `ModuleNotFoundError`。
2. **bash 默认无 pipefail**：`python -m report | tee file` 中 python 崩但 pipeline 退出码取 tee 的 0 → step 显示 success、输出为空、报告两段空白，CI 不报错。

**修复（`832ed5d`）**：eval job 自建 `uv venv .venv` + `GITHUB_PATH` 激活 + `uv pip install --python .venv/bin/python` 统一解释器与依赖；三个 run step 全加 `set -o pipefail`。lint/test job 零改动。重跑全绿，PR 评论三段完整。

### 4.2 测试集加载验证 → mock 冒烟跑（用户反馈「只列任务名，无每任务结果」）

原「Verify task set loads」只列 6 个任务名（验证文件能解析），不验证任务可用。升级为**冒烟跑**（`73dd856`）：每任务 mock 跑通 agent 循环 + judge，输出 OK/ERROR + `冒烟 N/N 任务管线可执行`。

**为什么 OK/ERROR 而非 PASS/FAIL**：mock 下 agent 不调工具，工具/标记/DB 断言必然 FAIL（实测 0/6），展示会误导成「评测全挂」；每任务真实判定（PASS/FAIL）由开发期 `--llm` 手动评测产出（#58 验收 6/6）。报告已标注此口径。

## 经验教训

1. **error.log 无记录 ≠ 日志没配**：可能是异常处理器某个分支没打日志（#64 的 detail 分支盲区）。排查先看 handler 各分支的日志覆盖。
2. **`hasattr(exc, "detail")` 判断 HTTPException 是坑**：SQLAlchemy 等 DB 异常自带 `detail` 属性（`[]`），必须用 `isinstance`。已修正 `fastapi-unified-error-handling` skill。
3. **fastapi.HTTPException 是独立类（子类关系）**：handler 内 isinstance 用 `StarletteHTTPException` 基类，已修正 skill。
4. **"Exception in ASGI application" 是 starlette 1.3.1 常态**（ServerErrorMiddleware 总是 re-raise），不是 handler 失效信号。
5. **dev-server 跑在 feat/56 分支（非 main）**：排查时注意进程加载的代码版本与 main 可能不同（本次恰好一致，但分支是 dev 工作分支）。
6. **连接池保活是 MySQL 生产标配**：`pool_pre_ping` + `pool_recycle`（< wait_timeout）防僵尸连接。
