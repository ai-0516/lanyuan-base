## # Dev — 实现总结

### 成果

1. **飞书群消息机制排查定案**（Issue #29）：
   - 平台侧：开通 `im:message.group_msg` 权限，非 @ 群消息才会推送到 bot（此前只开 `group_at_msg`，非 @ 消息在平台侧被过滤，`FEISHU_REQUIRE_MENTION=false` 无从生效）
   - Hermes 侧：`ALLOW_ALL_USERS=true` + `REQUIRE_MENTION=true`（单聊：@ 谁谁响应）+ `ALLOW_BOTS=mentions`（bot 间必须 @）
   - 配置管理：`.env` 改回符号链接指向 my-hermes 真源，避免独立文件漂移
2. **新 skill `feishu-group-mention-send`**：群里 @ 对方发消息的模板 + 纯文本硬性约束（带 markdown 会走 post 类型导致 `<at>` 不渲染）+ 验证方法
3. **`github-workflow` skill 加互通知流程**：PR 创建 → @dev-lead review → 修复通知 → merge 闭环（merge 信号来自用户）
4. **文档**：新写 `docs/feishu-workflow-automation.md`，本 daily 按新格式分 dev/dev-lead 两部分

### 决策记录

1. **bot 消息「点名制」、人类消息「广播制」**——`ALLOW_BOTS=mentions` + `REQUIRE_MENTION=true`，避免 bot 互相对话循环（曾因 `all` + `false` 配置发生循环对话事故）
2. **通知走 `hermes send` + `<at>` 纯文本透传**，不依赖 adapter 的 mention 构造能力
3. **merge 信号来自用户**，不是 dev-lead approve 自动触发

### 教训

- 飞书群聊里「消息没回应」先查**平台侧权限**（`group_msg`），再查 Hermes 准入——dedup 文件 `feishu_seen_message_ids.json` 在准入前记录所有到达消息，可区分「没到 adapter」vs「被拒」
- `.env` 独立文件会悄悄漂移，必须用符号链接指向真源
- 日志里没有 `[Mentioned:]` 前缀不代表消息没 @——`_build_mention_hint` 会跳过自己的 mention（is_self）
