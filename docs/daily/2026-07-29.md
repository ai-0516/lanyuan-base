## 关键决策

| 决策 | 方向 | 理由 |
|------|------|------|
| ATOF 存储格式 | 取代旧 JSONL 格式 | 事件级粒度，中断安全，可重放 |
| pool_size=1 替代 WAL | 单连接串行化 | 消除锁重试，MySQL 不受影响 |
| ATIF 严格按 RFC | 兼容 Harbor 生态 | 便于后续 SFT/RL 管线 |
| ATIF > ATOF 直接聚合 | 导出层映射 | ATOF 是运行时格式，不做存储双写 |

## 技术挑战

**SQLite 并发写锁** — WAL 模式减少了概率但未根除。最终方案是 `pool_size=1` 显式串行化，把 SQLite 单写者的本质显式表达，不做无谓的并发兜底。

**ATIF 格式对齐** — RFC v1.7 定义的工具调用格式（`function_name` + `arguments` Object）与 OpenAI 流式格式（`function: {name, arguments: string}`）不同，需要在导出层做转换。

## 经验教训

- **不要做预判性的并发容错**：`pool_size=10` 对 SQLite 只会增加锁冲突概率，显式单连接更诚实
- **按 RFC 做，不要自创格式**：虽然多花了一些时间对齐，但换来的是社区兼容
- **WAL 是场景工具，不是银弹**：单连接下 WAL 增加了文件管理复杂度（`.db-wal`、`.db-shm`）但无实际收益
